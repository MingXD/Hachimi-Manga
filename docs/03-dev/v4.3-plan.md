## 1. 多选后右键移动只动一个（bug）+ 其他右键操作排查

### 根因（已查实）
- 列表 `SelectionMode="Multiple"`（两处 ListBox），多选快捷键已生效：**Delete 键 / Ctrl+C / Ctrl+X 走 `MainWindow.SelectedEntries()` 全选批量**（`DeleteSelected` → `_vm.DeletePaths(paths)` 批量）
- **右键菜单的每一项都是 `FolderEntryItemViewModel` 自身命令**（`OpenCommand/CopyToCommand/MoveToCommand/RenameCommand/DeleteCommand/ShowInExplorerCommand/PropertiesCommand`）→ 只作用于右键点中的那一条，**不感知多选** → 移动/复制/删除/重命名/显示/属性全部只动一个（用户所说"删除可以多选"指的是 Delete 键）

### 方案
1. 右键菜单项统一改为**多选感知**（文件管理器行为）：
   - 右键点中的条目若**不在**当前选区 → 先选中它（单选）再执行
   - 若在选区 → 对**全部选中项**执行
2. 操作分档：
   | 菜单项 | 多选行为 |
   |---|---|
   | 复制到… / 移动到… | **批量**（一次选目标文件夹 → 逐个复制/移动 + 状态栏进度 x/y + 失败汇总） |
   | 删除（回收站） | **批量**（>1 项时弹一次确认「删除 N 项？」→ 逐个进回收站） |
   | 在资源管理器中显示 | 多选时打开**首个**（避免一次弹多个窗口；可备注） |
   | 打开 / 重命名 / 属性 | **单选**（多选时禁用灰色或仅作用于右键项） |
3. 实现：
   - `MainWindow.axaml` 两处菜单：`Command` → `Click` 事件（code-behind 统一 `OnContextMenuAction`），把条目级命令保留给单选快速路径
   - 批量复制/移动复用 `FileOps.CopyToAsync/MoveToAsync`（现成逐项 API）+ `MainWindowViewModel` 现有剪贴板批量的进度模式（`PasteClipboardAsync` 的写法）
   - 删除复用 `MainWindowViewModel.DeletePaths(paths)`（已支持批量）
4. 影响面：MainWindow（axaml 2 菜单 + code-behind 处理器 + VM 批量复制/移动 API 小改）；不改 FileOps 核心
5. 测试：headless 多选（`SelectedItems` 注入）→ 模拟菜单动作 → 断言多个条目被处理；单选回归

## 2. webp 漫画页显示很小（封面/正文）

### 根因（已实测确认）
- 用户库中该漫画页为 **VP8 有损 webp**（实测文件头：1280×1899）
- **`ImageInfo.ParseWebp` 的 VP8 分支解析错误**：把 VP8 帧的 start code（0x9D 01 2A）当成宽度读取、并误用 VP8L 的位打包公式 → 实测解析结果 **414×169**（比例 2.45 的横条）
- 布局按错误比例缩放 → 页面显示成"很扁很小"；**图片本身与解码（Skia）都正常**，仅文件头尺寸解析错
- 附带：VP8 的宽高字段不带 +1（现有 VP8L 分支的 +1 不影响 VP8L）

### 方案
```csharp
// VP8（有损）：payload[6..7]=宽 14bit LE，[8..9]=高 14bit LE（start code 在 [3..5]）
if (type == "VP8 " && dataStart + 10 <= head.Length)
{
    int w = head[dataStart + 6] | ((head[dataStart + 7] & 0x3F) << 8);
    int h = head[dataStart + 8] | ((head[dataStart + 9] & 0x3F) << 8);
    return w > 0 && h > 0 ? new PageSize(w, h) : null;
}
```
- 复核 VP8L（`data[1..4]` 位公式）与 VP8X（24bit canvas）分支，补长度边界检查
- 测试：真实样本断言 1280×1899；程序化 VP8/VP8L/VP8X 头部字节断言；回归既有 ImageInfo/浏览器测试
- 影响面：仅 `ImageInfo.cs`（webp 页比例）；缩略图（Skia 解码）本来正确，无需改

## 3. 文件夹自定义封面（作者文件夹选封面，保留全部文本）

### 需求语义
- 文件夹卡片：**保留** 文件夹名 / 子文件夹数 / 漫画数等全部文本
- 可**手动选取该文件夹下的一张图片**作为封面显示（不改变文件夹任何属性，不写任何文件）
- 记录"图片相对路径"；**图片被删/失效 → 自动回退原样式**（📁 图标），等下次手动重新选
- 只允许选取**该文件夹内**的图片

### 设计
**数据层（reading.db 新表，仅本地记录）**
```sql
CREATE TABLE IF NOT EXISTS FolderCovers (
    FolderPath TEXT PRIMARY KEY,   -- 文件夹绝对路径（规范化）
    RelPath    TEXT NOT NULL,      -- 相对该文件夹的图片路径（可含子目录）
    UpdatedAt  TEXT NOT NULL
);
```
- `ReadingStateStore` 加：`SetFolderCover(folderPath, relPath)` / `LoadFolderCover(folderPath)` / `ClearFolderCover(folderPath)`（`ReadingStateStore` 已有 db 连接，零新依赖）
- 校验（写入前）：`relPath` 不含 `..`、`Path.GetFullPath(combine(folder, relPath))` 必须仍落在文件夹内、扩展名 ∈ 图片集合、文件存在

**UI 层**
- 文件夹条目右键菜单新增（仅文件夹条目显示）：`设置封面…` / `清除封面`
- `设置封面…` 流程（V1）：系统文件选择器（`StorageProvider.OpenFilePicker`，筛选图片扩展名，初始目录=该文件夹）→ 选中后**路径校验**（必须在 folder.Path 下，否则提示拒绝）→ 存相对路径 → 刷新该条目封面
- 卡片显示（`MainWindow.axaml` 文件夹模板）：封面区尺寸**与漫画封面完全一致**（复用 `CoverWidth/CoverHeight`，随大/中/小模式缩放；默认大图模式约 164×200）→ 有封面显示图片（右下角可叠 📁 小角标），无封面/失效显示原 📁 大图标；**名称/副标题/统计行位置与样式不变**（文本永远显示）
- 详情模式（行式）不显示图片（保持 📁 图标，避免破坏行高）
- 回退：cover 记录存在但 `File.Exists` 失败 → 按无封面处理（不删记录，下次手动覆盖）

**缩略图**：`ThumbnailService` 新增 `GetImageThumbAsync(imagePath, width)`（任意图片路径 → 位图，弱引用缓存，不依赖 BookInfo）；目录加载时批量查 cover（`LoadFolderCovers(dirChildren)` 一次查询优化），前 24 个懒加载。

**封面区域大小评估（用户要求：比漫画封面矮，给三行文本留空间）**：
文件夹卡片有 3 行文本（名称 ≤2 行 + 副标题 + 统计行），比漫画卡片多一行 → 封面区高度取漫画封面的 ~3/4：

| 展示模式 | 文件夹封面区 | 漫画封面（对照） | 校验（封面+3行文本+边距 ≤ 卡片高） |
|---|---|---|---|
| 大图 | 216 × 232 | 216 × 309 | 232+98+12 = 342 ≤ 380 ✓ |
| 中图（默认） | 144 × 155 | 144 × 206 | 155+90+12 = 257 ≤ 272 ✓ |
| 小图 | 96 × 100 | 96 × 137 | 100+85+12 = 197 ≈ 196（小图模式标题收紧 2px 字体） |
| 详情（行式） | 不显示图片 | — | 保持 📁 图标 |

封面图 `UniformToFill`（填满裁切，视觉统一）；无封面/失效 → 原 📁 图标（尺寸 = 封面区高）。名称/副标题/统计文本位置样式**完全不变**。

**测试**：store 存取/清除/失效回退/路径校验（拒绝 ../、外部路径、非图片）；headless 设置后卡片显示（Thumbnail 非空）与文本保留；清除后回退。

## 4. 配对起点 1/2 强制配对（忽略页面大小）

### 现状（已查）
- `PageLayouter`：`CoverSingle` 恒单页 → `FirstPairOffset>0` 时第 2 页再单页 → 再按"横向页单页"规则成对
- `PairOffset=0`（"配对起点1"）实际渲染 = **第 1 页单页 + (2,3) 配对**
- `PairOffset=1`（"配对起点2"）实际渲染 = **第 1、2 页单页 + (3,4) 配对**
- 与用户预期都不符（用户要：起点1 → (1,2) 拼接；起点2 → 1 单张 + (2,3) 拼接；且**不考虑宽高**）

### 方案
- `PageLayoutOptions` 新增 `bool ForcePairing { get; init; } = false`（默认 false = 保持旧行为，测试不受影响）
- `PageLayouter.Layout` 分支：
  - `ForcePairing && FirstPairOffset==0`：从第 1 张开始**两两强制配对**（1+2, 3+4, …）；末张不足则单页；**忽略 CoverSingle / SpreadThreshold**
  - `ForcePairing && FirstPairOffset==1`：第 1 张单页，从第 2 张开始两两（2+3, 4+5, …）
- `ReaderViewModel.RebuildLayout` 传 `ForcePairing = true`
- UI 不变（工具栏"配对起点1/2"按钮沿用，语义对齐用户描述）
- 测试：`PageLayouterTests` 新增 ForcePairing 用例（起点1：第 1 逻辑页 (0,1)；起点2：第 1 逻辑页 (0,-1)、第 2 逻辑页 (1,2)；末张单页；宽页也成对）；**回归风险**：现有 E2E 双页断言基于"封面单页"（`ReaderE2eTests` 等）→ 需按新语义更新这些测试（封面页变双页、PageText/IsDoublePageShown 断言调整）
- 影响面：`PageLayouter`（选项+分支）、`ReaderViewModel`（1 行传参）、测试调整；双页阅读行为变化对**所有书**生效（用户明确要求）

### 为什么"有的书配对起点 1/2 完全一样、永远单拼"（用户观察的代码根因）
- 现有规则里 `SpreadThreshold = 1.6`：**宽高比 ≥1.6 的页面永远单页**（横向跨页图规则）
- 若某本书的**第 2 张是"宽页"**（或宽页在起始近旁）：配对起点1 的 (1,2) 被拆开成 1 单页 → 然后 (2,3) 配对；配对起点2 本来就是 (2,3) → **两档结果完全相同**
- **更常见的是 webp 那本书**：其页面比例解析错误（414×169 → 2.45）远超 1.6 → **每一页都被判成"横向页"→ 每页单拼**，配对起点怎么切都没用（与用户"似乎有的页面永远不拼接"完全吻合）
- 强制配对（忽略 SpreadThreshold/CoverSingle）彻底消除这一行为；webp 比例修复让正常竖页不再误判为横向页
